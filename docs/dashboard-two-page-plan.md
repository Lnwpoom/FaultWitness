# FaultWitness — แผน Dashboard สองหน้าแบบพอดีจอ

วันที่ 6 ตุลาคม 2026 · แผนรอบถัดไปบน branch `design/evidence-desk-v0`

สถานะ: ผู้ใช้ยืนยันให้นำ v2 แบบเลื่อนเฉพาะในช่องไปแทน Dashboard เดิมในโปรเจกต์แล้ว (7 ตุลาคม 2026) และสั่งจบงานโดยไม่ทดสอบจริงเพิ่ม

## ข้อกำหนดจากผู้ใช้

1. ใช้โครงแอปที่มีเมนูซ้ายตามภาพที่ 1
2. มีเมนูหลักสองปุ่ม: หน้าแรกแสดงเฉพาะส่วนสรุป/หลักฐาน/คำแนะนำตามภาพที่ 2; หน้าที่สองแสดงเฉพาะผลการตรวจดิบตามภาพที่ 3
3. แต่ละหน้าอยู่ภายในพื้นที่เบราว์เซอร์ ไม่ต้องเลื่อนลงเพื่อดูส่วนที่หลุดกรอบ
4. เปลี่ยนปุ่ม Tweaks ใหญ่เป็นไอคอนเล็ก และแยกการเลือกธีมออกจากขนาดสำหรับผู้ชม
5. ใช้ฟอนต์จาก ZIP ที่ผู้ใช้ระบุ

## สิ่งที่อ่านจากภาพอ้างอิง

ภาพที่ 1 ให้แนวทางด้านโครงสร้าง: แถบเมนูซ้ายแนวตั้ง พื้นเมนูแยกจากพื้นที่ทำงาน ปุ่มไอคอนมีสถานะเลือกชัดเจน และกรอบเนื้อหาที่มีขอบมน ส่วน avatar, สมาชิก, search และ task controls ไม่เกี่ยวกับ FaultWitness จึงไม่เพิ่มเข้ามา

ผู้ใช้ยืนยันให้อ้างอิงเฉพาะโครงและเมนู ไม่ใช้โทนพาสเทลหรือพื้นไล่สี; คงสี FaultWitness เดิม

ภาพที่ 2 กับภาพที่ 3 คือสองมุมมองของ Report ชุดเดียวกัน การเปลี่ยนเมนูต้องไม่เริ่ม Round ใหม่ ไม่รีเซ็ตข้อมูล และไม่ทำให้รายงานของทั้งสองหน้าเป็นคนละรอบ

## โครงหน้าที่เสนอ

### แถบเมนูซ้าย

- กว้างเริ่มต้น 80px บนเดสก์ท็อป มีสองรายการ: **ผลวิเคราะห์** และ **ผลตรวจดิบ**
- ใช้ไอคอนเส้นขนาดประมาณ 20–22px พร้อมชื่อสั้นใต้ไอคอน เพื่อให้ผู้ชมรู้หน้าที่โดยไม่ต้องเดา
- พื้นที่กดอย่างน้อย 44×44px; แสดง active, hover และ keyboard focus แยกจากกัน
- เปลี่ยนหน้าภายในแอปผ่านสถานะมุมมอง พร้อม deep link `#overview` / `#results` โดยยังคง URL หลัก `/` และ `/index.html`
- ชื่อ FaultWitness อยู่ในหัวแอป คงเครื่องหมายเดิมแบบข้อความ ไม่สร้างโลโก้ใหม่จากภาพตัวอย่าง

### หน้า 1 — ผลวิเคราะห์

หัวแอปแสดงชื่อ หน้าใช้งาน การเชื่อมต่อ และปุ่มตรวจเดี๋ยวนี้ในแถวกระชับ ตามด้วยแถบข้อสรุปที่สั้นลง

พื้นที่หลักยังใช้ Witness Pair ที่ผู้ใช้เลือก: ฝั่งซ้ายเปรียบเทียบ A/B ตามปลายทาง ฝั่งขวาแสดงหลักฐาน สิ่งที่ยังไม่รู้ และสิ่งที่ควรตรวจต่อ ทั้งหมดอยู่ในพื้นที่ความสูงที่เหลือของหน้าต่าง

- รวมชื่อปลายทางเป็นหัวกลุ่ม ลดการซ้ำข้อความและระยะว่างที่กินความสูง
- ปรับ header ของ Probe ให้กระชับและให้ตารางครบ 7 รายการอยู่ในกรอบเป้าหมาย
- ตัดส่วนผลดิบออกจากหน้านี้โดยสมบูรณ์
- หากมีหลาย Finding ให้แสดงครบในช่องคำอธิบายที่เลื่อนได้ ไม่ยืดหน้าลงล่าง หัวสถานะรวมต้องยังบอกว่ามีหลายข้อสรุป
- ถ้ารายละเอียดยาวกว่าพื้นที่ ให้เลื่อนในช่องคำอธิบายโดยตรง รวมทั้งโหมดนำเสนอ ไม่มีปุ่มแบ่งหน้าและไม่ตัดข้อความ
- Observation ต้องยังแยกจาก Finding และเข้าถึงได้ครบ

### หน้า 2 — ผลตรวจดิบ

- ใช้พื้นที่ทำงานเต็มความกว้างข้าง sidebar; ไม่มี hero ผลวิเคราะห์หรือส่วนเหตุผลซ้ำ
- หัวหน้าแสดง “ผลตรวจดิบ”, เลขรอบ, จำนวนแถว และป้ายความสด/เพื่ออ้างอิง
- คงครบทั้ง 9 คอลัมน์จาก Report: probe_id, round_id, target, test, success, duration_ms, error_type, started_at, finished_at
- แถวทั้งหมดในรอบปกติ 6 แถว และรอบตรวจครบ 14 แถวต้องเข้าถึงได้ เมื่อพื้นที่ไม่พอให้เลื่อนภายในช่องตาราง ไม่เพิ่ม page scroll
- คอลัมน์เวลาคงค่าเดิมครบ; บนพื้นที่แคบอาจห่อบรรทัดตัวเลขอย่างควบคุมหรือใช้มุมมองรายละเอียดแถว ห้ามตัด timestamp จนอ่านค่าไม่ครบ
- แสดงจำนวนแถวทั้งหมด; หัวตารางค้างขณะเลื่อน ไม่มีปุ่มก่อน/ถัดไป
- เมื่อข้อมูลใหม่เข้ามา คงตำแหน่งเลื่อนเท่าที่ข้อมูลอนุญาต และแสดงเลขรอบใหม่อย่างชัดเจน (สำหรับขั้นเชื่อมระบบสด)

## เงื่อนไขพอดีจอ

คำว่า “ขนาดมาตรฐานเบราว์เซอร์” ไม่มีขนาดตายตัว แผนเริ่มต้นจะยึด **พื้นที่เนื้อหาเว็บ** ที่ 1366×650, 1440×800 และ 1920×900 CSS px ที่ zoom 100% โดยไม่รวมแถบแท็บและ address bar ของเบราว์เซอร์

- App shell สูงตาม viewport (`100dvh`) มี sidebar, header, content และแถบควบคุมที่แบ่งพื้นที่แน่นอน
- ห้ามแก้ด้วย `overflow:hidden` แล้วปล่อยข้อมูลล้นออกไป ต้องให้ข้อมูลทุกส่วนเข้าถึงได้ด้วยการเลื่อนภายในช่อง
- ในโหมดมาตรฐานใช้เนื้อหาประมาณ 16–18px; โหมดนำเสนอประมาณ 22–24px แล้วให้เลื่อนภายในช่องเพื่ออ่านข้อมูลส่วนที่เหลือ
- ใช้ CSS ปรับพื้นที่เลื่อนตามขนาดหน้าต่างและฟอนต์ โดยไม่สร้างเนื้อหาใหม่หรือรีเซ็ตตำแหน่งอ่าน
- หน้าเว็บไม่เลื่อน; ช่องหลักฐาน คำอธิบาย และผลดิบเลื่อนแยกกันด้วยเมาส์ แทร็กแพด หรือคีย์บอร์ด และไม่ส่งต่อการเลื่อนไปยังหน้าเว็บ
- จอแคบหรือ browser zoom สูงต้องมี layout ที่อ่านได้และพื้นที่เลื่อนภายในช่อง ไม่รับประกันว่าข้อมูลทั้งหมดจะปรากฏพร้อมกันในทุกความละเอียด

## ปุ่มแสดงผล

แทนปุ่ม Tweaks ขนาดใหญ่ด้วยไอคอนแยกที่มุมขวาล่าง โดยสำรองพื้นที่ไว้ไม่ให้บังแถวข้อมูล:

1. **ธีม:** ไอคอนดวงอาทิตย์/ดวงจันทร์ เปิดตัวเลือก สว่าง / มืด / ตามเครื่อง
2. **ขนาดสำหรับผู้ชม:** ไอคอน Aa หรือจอภาพ เปิดตัวเลือก มาตรฐาน / นำเสนอ
3. **ตัวเลือกอื่น:** หากต้องคงการเน้นผลไม่ผ่าน ใช้ไอคอนปรับแต่งเล็กแยกต่างหาก โดยไม่รวมธีมและขนาดกลับมาในแผงเดียว

ตัวไอคอนเล็กประมาณ 20px แต่กรอบกดยังอย่างน้อย 44px พร้อม tooltip, accessible name, focus และ Escape เพื่อปิด popover การเลือกต้องจำไว้ทั้งสองหน้าเหมือนกัน

## Design Read

- Artifact: Dashboard สองหน้าสำหรับการเดโม
- Audience: กรรมการและผู้ชมที่ต้องเข้าใจภาพรวมเร็ว
- Visual language: กรอบแอปที่มี sidebar แบบภาพอ้างอิง + แผงพยานคู่ A/B
- Mode: Redesign · Preserve คุณค่าผลิตภัณฑ์และระบบข้อมูล โดยเปลี่ยนการแบ่งหน้าและองค์ประกอบตามคำขอ
- Dials: variance 5, motion 2, density 7, asset dependence 3, brand fidelity 7
- ผลของ dials: ใช้โครงนำทางคงที่ ขยับภาพน้อย เพิ่มข้อมูลที่อ่านได้ต่อจอ และรักษาสี/ชื่อ/ความหมายเดิมตามที่ผู้ใช้ยืนยัน

บทบาทหน้าจอ: หน้าผลวิเคราะห์ใช้เล่าเหตุผล; หน้าผลดิบใช้ตรวจสอบหลักฐาน ระยะมองคือโน้ตบุ๊กและจอเดโมใหญ่ อารมณ์ภาพควรสงบและอ่านง่าย ขอบเขตความจุแก้ด้วยการเลื่อนภายในช่องและลำดับชั้น ไม่ย่อข้อความจนเล็ก

## ระบบภาพเริ่มต้นเพื่อยืนยัน

- Palette: คง warm neutral + teal เดิม; light `#FAFAF9` / `#FFFFFF` / `#1C1917`, dark `#1C1917` / `#262220` / `#F5F5F4`, accent `#0F766E` / `#5EEAD4`
- Typography: Block Craft สำหรับชื่อแอปและ A/B; IBM Plex Sans Thai สำหรับภาษาไทย เนื่องจาก Block Craft ไม่มีอักษรไทย
- Spacing: ฐาน 4px; ใช้ 8 / 12 / 16 / 24 เป็นหลักในหน้าเต็มจอ
- Radius: sidebar/frame 16px, surface 12px, control 8px ให้ใกล้โครงภาพอ้างอิงมากขึ้น
- Shadow: ใช้เฉพาะ popover เบา ๆ; ตารางไม่เพิ่มเงาหรือสีตกแต่งที่รบกวนสถานะ
- Motion: เปลี่ยนหน้า/เปิด popover 120–160ms; reduced motion ปิด transition

## ลำดับดำเนินงาน

1. ยืนยันการตีความโทนสีและไฟล์ฟอนต์ให้ตรงกัน
2. ทำ v2 draft ที่มี sidebar และสองหน้าให้เห็นความพอดีของกรอบก่อนเชื่อมครบทุก state เก็บ v0 และหน้าเดิมผ่าน version control
3. ให้ผู้ใช้เห็นและปรับองค์ประกอบของ v2 ตาม checkpoint ของสกิล
4. นำไปใช้จริง: แบ่งมุมมอง, internal scrolling, แยกปุ่มแสดงผล, font assets และคงการอัปเดต Report ร่วมกัน
5. ตรวจตามเกณฑ์พอดีจอและการอ่านข้อมูลครบ โดยแยกผลตรวจจริงออกจากสมมติฐาน; ตรวจ API/Diagnosis เดิมตามมาตรฐาน repo

Protected contracts: กฎ Diagnosis, Report/Result schema, ปุ่มตรวจเดี๋ยวนี้, polling, stale/disconnected semantics, การเก็บข้อมูลครบ, routes เดิม และค่าการตั้งค่าที่มีอยู่ การเพิ่มสองมุมมองและเมนูเป็นการเปลี่ยน IA ที่ผู้ใช้ขอแล้ว ไม่ต้องขออนุญาตซ้ำในประเด็นนั้น

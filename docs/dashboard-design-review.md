# FaultWitness — ประเมิน Dashboard และแผนออกแบบใหม่

วันที่ 6 ตุลาคม 2026 · สถานะ: ผู้ใช้เลือกแบบที่ 2 Witness Pair และนำไปพัฒนา Dashboard จริงใน branch `design/evidence-desk-v0`

บริบทที่ผู้ใช้ยืนยัน: **ใช้เดโมให้กรรมการหรือผู้ชมเข้าใจปัญหาได้เร็ว**

## 1. ข้อสรุป

Dashboard มีรากฐานด้านความน่าเชื่อถือดี: มีหลักฐานจาก Probe สองจุด แยกข้อสรุปออกจากข้อสังเกต บอกสิ่งที่ยังไม่รู้ และไม่ใช้ผลเก่าแทนสถานะปัจจุบัน แต่ภาพรวมยังเป็นหน้ารายงานที่ผู้ชมต้องอ่านเอง จุดขายเรื่อง “พยานสองจุดช่วยหาบริเวณที่เสีย” ยังไม่กลายเป็นโครงสร้างภาพที่จดจำได้

แนะนำทิศทาง **Evidence Desk — โต๊ะวิเคราะห์หลักฐาน** โดยใช้ภาพเปรียบเทียบ A/B เป็นลายเซ็นของผลิตภัณฑ์ ให้ข้อสรุปที่เฉพาะเจาะจงนำสายตา ตามด้วยหลักฐานและสิ่งที่ควรตรวจต่อ เป้าหมายคือให้ผู้ชมอธิบายกลับได้ภายใน 5–10 วินาที เป้าหมายนี้ยังไม่ได้ทดสอบกับผู้ใช้

## 4. สิ่งที่ควรเก็บไว้

1. **ภาษาไทยที่อธิบายเหตุผลและยอมรับข้อจำกัด** โดยเก็บ `supporting`, `missing`, `next_steps` ครบ ไม่เปลี่ยนเป็นเปอร์เซ็นต์ความมั่นใจที่ระบบไม่ได้คำนวณ
2. **Probe A/B เปรียบเทียบในรอบเดียวกัน** เป็นคุณค่าหลักและควรเป็นแกนทางภาพ
3. **สถานะผลเก่าและข้อมูลยังไม่พอ** แสดงเด่นก่อนหลักฐานเก่าเสมอ
4. **ปุ่ม “ตรวจเดี๋ยวนี้”** มีการป้องกันกดซ้ำและข้อความระหว่างตรวจอยู่แล้ว
5. **ผลการตรวจดิบที่เปิดดูได้** ช่วยตอบคำถามกรรมการและรักษาความโปร่งใส
6. **สี teal และพื้นโทนอุ่น** เป็นฐานที่ต่อยอดได้ และหน้าเดิมไม่พึ่ง CDN เหมาะกับการเดโมออฟไลน์

## 5. ปัญหาที่ควรแก้ตามลำดับ

### 1 — สำคัญสูง: แยกความสดของข้อมูลออกจากการเชื่อมต่อ

ในภาพผลเก่า ด้านบนยังมีจุดเขียว “อัปเดตอัตโนมัติทุก 2 วินาที” ขณะที่ผลตรวจไม่มีข้อมูลใหม่ ทั้งสองข้อความถูกต้องคนละบริบท แต่ผู้ชมอาจตีความว่าระบบเครือข่ายยังปกติ อีกกรณีคือเมื่อ fetch ล้มเหลว `setConnection()` แสดง notice แต่คงข้อสรุปและอายุข้อมูลจาก report เดิมบนจอ (`index.html:252–264`)

**แก้:** แยกข้อความ “เชื่อมต่อเครื่องหลัก” ออกจาก “ผลตรวจล่าสุด” เมื่อขาดการเชื่อมต่อให้สรุปด้านบนว่าไม่สามารถยืนยันสถานะปัจจุบันได้ เก็บผลก่อนหน้าใต้ป้ายอ้างอิง และแสดงเวลารับข้อมูลล่าสุด ห้ามตีความการขาดการเชื่อมต่อของเบราว์เซอร์ว่า Probe หรือเครือข่ายเสีย ห้าม hard-code เกณฑ์ stale 25 วินาที เพราะเป็น config ของระบบ

### 2 — สำคัญสูง: ทำให้ข้อสรุปเฉพาะเจาะจงเป็นจุดเริ่มอ่าน

ภาพใบรับรองใช้ “ปลายทางหนึ่งผิดปกติ” เป็นข้อความใหญ่ แต่ “เว็บไซต์ X ตอบกลับ แต่ใบรับรองไม่ผ่าน” เล็กลงมากและอยู่ในกล่องล่าง ผู้ชมต้องอ่านสองตำแหน่งเพื่อเข้าใจประเด็น (`index.html:170–198`)

**แก้:** ใช้ `overall` เป็นหมวดสถานะ และยก `finding.title` เดิมเป็นข้อความหลักเมื่อมีข้อสรุปเดียว โดยไม่เขียนเหตุผลใหม่เอง หากมีหลายข้อสรุปให้แสดงจำนวนและหัวข้อทุกข้อ ไม่มีการเลือกข้อเดียวแล้วซ่อนที่เหลือ กรณี stale ให้สถานะข้อมูลเก่านำก่อนข้อสรุปเดิม

### 3 — สำคัญ: ทำให้การเทียบ A/B เป็นภาพจำ

ตารางมีข้อมูลดี แต่ข้อความชื่อปลายทางยาวและซ้ำทุกแถว ผู้ชมต้องไล่ข้อความเพื่อจับว่า A ล้มเหลวแต่ B ผ่าน หรือทั้งคู่ผิดปกติที่ X (`index.html:127–128, 206–213`)

**แก้:** จัดแถวเป็นกลุ่มบริการภายใน / เว็บไซต์ X / เว็บไซต์ Y และยึด A/B เป็นคอลัมน์คงที่ มี HTTP(S), DNS และ TCP เป็นแถวย่อย ใช้ข้อความ ผ่าน / ไม่ผ่าน / ไม่ได้ตรวจ / ไม่มีผล ให้ต่างกันชัดเจน เวลาตอบสนองเป็นข้อมูลรอง รูปแบบนี้เป็น “แผงเปรียบเทียบหลักฐาน” ไม่อ้างว่าเป็นแผนผังสายเครือข่ายจริง เพราะ API ไม่มี physical topology

### 4 — สำคัญ: ลดสีที่สื่อความหมายปะปน

`.tag.lv-confirmed` ใช้สีเขียวเหมือนการทดสอบผ่าน แม้กำลังยืนยันว่ามีปัญหา (`index.html:75`) และสีเขียว “ส่งผลล่าสุด” ในหัว Probe อยู่ใกล้ผลทดสอบที่ล้มเหลว

**แก้:** ระดับหลักฐานใช้ข้อความกับเส้น/น้ำหนักตัวอักษรและสี teal; เขียวใช้กับผลทดสอบที่ผ่าน; แดงกับผลไม่ผ่านหรือแจ้งเตือน; amber กับข้อมูลไม่พอ/ผลเก่า ส่วนการส่งผลของ Probe ใช้ข้อความชัดเจน ไม่ใช้จุดสีโดด ๆ ระดับ `confirmed` ไม่ได้หมายถึงรู้ต้นเหตุทั้งหมดหรือมีความมั่นใจ 100%

### 5 — สำคัญ: ทำให้หลักฐานและสิ่งที่ควรตรวจต่ออ่านจากจอใหญ่ได้

`.cols` ใช้คอลัมน์ขั้นต่ำ 210px ภาพจริงจึงเกิดย่อหน้าไทยแคบและ “ตรวจต่อที่แนะนำ” ตกลงแถวถัดไป ขอบ panel และ finding ซ้อนกันหลายชั้นเพิ่มน้ำหนักให้ภาชนะมากกว่าเนื้อหา (`index.html:48, 68–72`)

**แก้:** จัดเนื้อหาหลักเป็นบล็อกแนวตั้งตามลำดับ “หลักฐานที่สนับสนุน → หลักฐานที่ยังขาด → ตรวจต่อที่แนะนำ” ใช้เส้นแบ่งและช่องไฟแทนกล่องซ้อน จัดรายการตรวจต่อเป็นลำดับตามข้อมูลเดิม รายละเอียดทั้งหมดต้องยังเข้าถึงได้ ไม่ย่อด้วยการตัดข้อความออก

### 6 — สำคัญ: คงความอ่านได้ของข้อมูลอ้างอิงและการโต้ตอบ

`.dim { opacity:.5 }` ทำให้ผลเก่าซีดทั้งตารางในภาพจริง (`index.html:78`) และทุก poll เขียน `dash.innerHTML` ใหม่ แม้ `rawOpen` คงอยู่ แต่ node ที่ผู้ใช้กำลัง focus หรือเลือกข้อความอาจถูกแทนที่ (`index.html:238–249`) ยังไม่มี `:focus-visible` ที่ออกแบบเฉพาะ; ไม่ได้หมายความว่า browser default focus หายไปแล้ว

**แก้:** ใช้ป้าย “ผลเก่าเพื่ออ้างอิง” และพื้นรองที่อ่านได้ แทนลด opacity ทั้งเนื้อหา อัปเดตเฉพาะค่าที่เปลี่ยนหรือคง focus/selection/open state อย่างมีแบบแผน เพิ่ม focus ring และประกาศผ่าน live region เฉพาะการเปลี่ยนสถานะสำคัญ ไม่อ่านอายุข้อมูลซ้ำทุก 2 วินาที

### 7 — ปรับความประณีต: สร้างระบบภาพสำหรับการเดโม

มี dark mode อัตโนมัติแล้ว แต่ไม่มีตัวเลือกบนจอ ตัวอักษรขึ้นกับฟอนต์ที่ติดตั้งในเครื่อง และ spacing กระจายหลายค่า (`index.html:15–25, 32–88`)

**แก้:** รวมสี ระยะ และ typography เป็น tokens; เพิ่มตัวเลือก สว่าง / มืด / ตามเครื่อง; เลือกฟอนต์ไทยที่อ่านไกลได้และบรรจุไว้กับงานเมื่อสิทธิ์อนุญาต โดยยังรักษาการเดโมออฟไลน์

## 6. แนวทางสร้างเอกลักษณ์: Evidence Desk

**แนวคิด:** FaultWitness คือพื้นที่เปรียบเทียบคำให้การของ Probe สองจุด ลายเซ็นของหน้าจอมาจากคู่ A/B ที่จัดแนวตรงกัน การแสดงหลักฐานที่ขัดแย้งหรือสอดคล้อง และข้อสรุปที่ตรวจย้อนกลับได้

องค์ประกอบเฉพาะตัว:

- **คู่พยาน A/B:** ทุกปลายทางใช้จังหวะคอลัมน์เดียวกัน สแกนความต่างได้ทันที
- **ข้อสรุปพร้อมหลักฐาน:** หัวข้อเฉพาะเจาะจงติดกับระดับหลักฐานและจำนวนรอบที่พบจริง
- **พื้นที่ “ยังไม่รู้”:** รักษาตำแหน่งที่มองเห็นได้ เพราะความซื่อตรงต่อข้อจำกัดเป็นส่วนหนึ่งของตัวตนผลิตภัณฑ์
- **อ้างอิงเป็นรอบ:** ใช้เลขรอบจริงเชื่อมข้อสรุป ตาราง และผลดิบ ไม่สร้างเส้นเวลาในอดีตขึ้นจาก report รอบเดียว

โครงร่างหน้าจอที่เสนอ ใช้ข้อมูลเดิมทั้งหมด:

```text
FaultWitness            เชื่อมต่อเครื่องหลัก · ผลล่าสุด       ตรวจเดี๋ยวนี้
──────────────────────────────────────────────────────────────────────
หมวดสถานะ · ระดับหลักฐาน · จำนวนรอบจริง
ข้อสรุปที่เฉพาะเจาะจง / สถานะข้อมูลเก่าเมื่อมี
───────────────────────────────────────────┬──────────────────────────
หลักฐานเปรียบเทียบ                          │ ทำไมจึงสรุปเช่นนี้
                     Probe A     Probe B   │ หลักฐานที่สนับสนุน
บริการภายใน                                │ หลักฐานที่ยังขาด
เว็บไซต์ X                                 │ ตรวจต่อที่แนะนำ
  HTTPS / DNS / TCP                        │
เว็บไซต์ Y                                 │ ข้อสรุปอื่นเมื่อมีหลายข้อ
  HTTPS / DNS / TCP                        │ ข้อสังเกตแยกจากข้อสรุป
───────────────────────────────────────────┴──────────────────────────
รอบ / เวลา / จำนวนการทดสอบ              เปิดผลการตรวจดิบ
```

ให้แผงเปรียบเทียบประมาณ 58% และคำอธิบาย 42% เป็นจุดเริ่มทดลอง ข้อความยาวให้หน้าเลื่อนได้ ห้ามบีบฟอนต์เพื่อให้ทุกสถานการณ์พอดีจอ หากจอแคบให้เรียงข้อสรุป → หลักฐาน → ตรวจต่อ และคง A/B เคียงกันในตารางที่เลื่อนแนวนอนได้เฉพาะส่วน

| Information density | 6/10 | สรุปอ่านจากจอใหญ่ รายละเอียดเชิงเทคนิคเปิดดูได้โดยข้อมูลไม่หาย |
| Asset dependence | 2/10 | อัตลักษณ์มาจาก typography และข้อมูล ไม่ต้องมีภาพตกแต่ง |
| Brand fidelity | 6/10 | คงชื่อ FaultWitness ภาษาไทย โทนอุ่นและ teal แต่ปรับองค์ประกอบใหม่ |

ก่อนเลือก tokens:

- **บทบาทหน้าจอ:** สาธิตข้อสรุปและพิสูจน์ด้วยหลักฐาน
- **ระยะมอง:** โน้ตบุ๊กของผู้สาธิตและจอใหญ่ของผู้ชม ต้องทดลองอ่านจากตำแหน่งผู้ชมจริง
- **อารมณ์ภาพ:** สุขุม ชัดเจน แม่นยำ ไม่เร่งเร้าด้วยสีเตือนเต็มหน้า
- **ความจุ:** หนึ่งข้อสรุปหลัก + A/B + สิ่งที่ตรวจต่อในมุมมองแรก; ข้อสรุปหลายข้อและหลักฐานยาวใช้พื้นที่ต่อเนื่อง ไม่ตัดทิ้ง

## 8. แผนดำเนินงาน

### ระยะ 1 — v0 สำหรับตัดสินใจเรื่ององค์ประกอบ

หลังยืนยันทิศทาง สร้าง HTML แยกจากหน้าจริงและใช้ภาพ/Report ที่บันทึกจากระบบจริงเป็นหลักฐาน ระบุว่าเป็นข้อมูลย้อนหลัง ไม่อ้างเป็นสถานะสด ทำ 3 องค์ประกอบในไฟล์เดียวผ่าน Tweaks:

1. **Conclusion first:** ข้อสรุปและสิ่งที่ตรวจต่อเด่นที่สุด เหมาะกับผู้ชมที่ไม่รู้เครือข่าย
2. **Witness Pair — แนะนำ:** แผง A/B เป็นพื้นที่หลักและเหตุผลอยู่ข้างกัน ทำให้ผู้ชมเห็นวิธีคิดของผลิตภัณฑ์
3. **Evidence sequence:** เรียงข้อสรุป → หลักฐาน → ตรวจต่อในแนวตั้ง เหมาะกับจอที่แคบกว่า

ความต่างอยู่ที่ลำดับสายตาและพื้นที่ ไม่ใช่แค่สลับสี ตั้งต้นด้วยกรณี dnsA, certX และ stale; หากยังไม่มี Report fixture ที่ตรงกับภาพให้ดึงจากผลที่บันทึก/ระบบก่อน ไม่แต่งข้อมูลขึ้นเอง v0 ใช้ placeholder ในส่วนที่ยังไม่มีข้อมูลพร้อมระบุชัดเจน

**จุดส่งมอบ:** เปิดดูทิศทางได้เร็ว พร้อมข้อสมมติและข้อมูลที่ยังขาด แล้วให้ผู้ใช้เลือกหรือผสมองค์ประกอบก่อนทำเต็ม

### ระยะ 2 — แก้ความหมายและการอ่านข้อมูล

- แยกสถานะเชื่อมต่อ, ความสด, สถานะผลวิเคราะห์ และระดับหลักฐาน
- ปรับหัวข้อหลัก การรวมแถวตามปลายทาง และตำแหน่ง next steps
- ลดกล่องซ้อน และยกเลิกการลด opacity ของหลักฐานเก่าทั้งก้อน
- แสดง no-data, stale, disconnected, multiple findings และ observation-only อย่างตรงกับข้อมูล

### ระยะ 3 — นำระบบภาพไปใช้จริง

- ใช้ tokens และฟอนต์ที่ยืนยันแล้ว; เพิ่มตัวเลือกธีมและขนาดสำหรับนำเสนอ
- ปรับ render ให้ไม่รบกวน focus/การอ่านข้อความ/การเปิดผลดิบระหว่าง polling
- เพิ่ม focus-visible, semantic headings, table caption/header association และการประกาศสถานะเท่าที่จำเป็น
- คง HTML/JavaScript เดิมเป็นฐาน ไม่จำเป็นต้องย้าย framework เพื่อแก้การออกแบบนี้

### ระยะ 4 — ตรวจงานตามขอบเขตการพัฒนา

- เมื่อแก้โค้ด: ทำ typecheck, lint และชุดทดสอบตามมาตรฐาน repo; behavioral changes เขียน tests ก่อนตามข้อกำหนดโครงการ
- เมื่อสร้างฟีเจอร์เสร็จ: ตรวจ Docker Lab ตาม definition of done ที่เกี่ยวข้อง
- เสนอ browser acceptance แยกเมื่อผู้ใช้สั่งทดสอบ: จอเดโม 1440×900 / 1920×1080, laptop 1280×800, narrow 390px, light/dark, keyboard และ polling ขณะเปิดรายละเอียด
- การทดสอบกับผู้ชม: ให้คนที่ยังไม่รู้ระบบดู dnsA/certX/stale แล้วบอกตำแหน่งปัญหา หลักฐาน และสิ่งที่ควรตรวจต่อ เป้าหมายเริ่มต้น 5–10 วินาที ไม่ใช้คะแนนความสวยแทนความเข้าใจ

## 9. สัญญาที่ต้องรักษาและความเสี่ยง

**Preserve:** `GET /`, `/index.html`, `GET /report`, `POST /rounds`; รูปแบบ `Report`/`NoDataReport`; ปุ่มตรวจเดี๋ยวนี้; การ polling; ตัวป้องกัน report ย้อนหลัง; คำศัพท์และข้อความไทยจากระบบ; หลักฐาน/ข้อจำกัด/ผลดิบทุกข้อ; การแยก observation; กฎ alerts และ stale ของ backend

**Improve:** การนำเสนอข้อมูล ลำดับสายตา สีตามความหมาย readability และความต่อเนื่องของ interaction

**Remove:** กล่องซ้อนที่ไม่ช่วยจัดกลุ่ม, metadata ซ้ำ, การใช้สี success กับระดับหลักฐาน, การลด opacity จนอ่านข้อมูลอ้างอิงยาก

**ความเสี่ยงสูงสุด:** แผนภาพที่ทำให้เข้าใจว่ารู้ topology/สาเหตุแน่นอนเกินหลักฐาน จึงใช้แผงเปรียบเทียบผลจริงและข้อความจาก backend โดยไม่ให้ frontend วินิจฉัยสาเหตุใหม่

**ข้อจำกัดข้อมูล:** Report มีผลรอบล่าสุดและจำนวนรอบที่พบ แต่ไม่มี series ประวัติครบสำหรับกราฟย้อนหลัง ไม่มี confidence percentage และไม่มี uptime ดังนั้นไม่เพิ่มกราฟ/เกจดังกล่าวในงานนี้

**ข้อจำกัดออฟไลน์:** Collector ปัจจุบันเสิร์ฟหน้า HTML และ API ตาม routes ที่ระบุ ไม่ได้เสิร์ฟโฟลเดอร์ฟอนต์ทั่วไป หากเลือก custom font ให้ฝังไฟล์ที่อนุญาตลง HTML หรือวางแผน route asset ที่จำกัดขอบเขตโดยชัดเจน ห้ามเพิ่มลิงก์ฟอนต์แล้วสมมติว่าโหลดได้

**Rollback:** v0 อยู่แยกจาก production; เมื่อพัฒนาจริงแยก commit ด้านความหมายข้อมูลกับด้านภาพ และเก็บหน้าเดิมผ่าน version control

1. ยก `finding.title` เป็นข้อความหลักเมื่อมีข้อสรุปเดียว และวาง `overall` เป็นหมวดรอง

## 11. สิ่งที่นำไปใช้จริงหลังเลือกแบบที่ 2

- ใช้ Witness Pair ใน `src/dashboard/index.html` พร้อม `GET /report` และ `POST /rounds` เดิม ไม่มีตัวเลือกสถานการณ์จำลองในหน้าจริง
- ข้อสรุปเฉพาะเจาะจงนำสายตา; หลักฐาน A/B จัดกลุ่มตามปลายทาง; ข้อสรุปหลายข้อแสดงครบพร้อมระดับหลักฐานและคำแนะนำของแต่ละข้อ
- แยก disconnected / stale / no-data / initial / alert / observation; ผลเก่าอ่านได้และมีป้ายอ้างอิง
- อัปเดต DOM เดิมตามค่าที่เปลี่ยน เก็บ disclosure ของผลดิบและ scroll container ไว้; ป้องกัน response เก่าย้อนทับผลใหม่ด้วยลำดับ request และเวลา Collector
- เพิ่ม timeout ของคำขอเพื่อไม่ให้ปุ่มหรือ polling ค้างตลอดไป; ความล้มเหลวในการสั่งตรวจแสดงต่างจากการขาดการเชื่อมต่อ
- Tweaks มี theme ตามเครื่อง/สว่าง/มืด, ขนาดนำเสนอ, การเน้นผลไม่ผ่าน และบันทึก preference แบบ local โดยมี fallback เมื่อ storage ใช้ไม่ได้
- เสิร์ฟฟอนต์และ OFL จาก routes ที่ระบุชื่อไฟล์แน่นอน ไม่เปิด directory สำหรับอ่านไฟล์ทั่วไป; `npm run build` รวมหน้าและ assets ไปใน `dist/dashboard`
- เก็บ v0 เดิมไว้เปรียบเทียบ โดยไม่ใช้ข้อมูลย้อนหลังในหน้า production
